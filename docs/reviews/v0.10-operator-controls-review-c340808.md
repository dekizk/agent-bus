## Verdict

**The architectural direction is good, but harden control-state correctness before adding fairness or budgets.**

Immutable priority and delayed eligibility, event-sourced pause/resume, explicit supersession, and evidence-backed operator explanations fit the existing design. The release-blocking concern is that the running PM can disagree with a fresh ordered replay of the same persisted history.

## 1. High — Running PM state can diverge from ordered replay

**Locations:** `pm_agent.py:478–487`, `pm_agent.py:510–516`; related resume precondition at `projection.py:656–668`.

### Reproduction

Persisted log:

```text
#1 task.created
#2 task.pause_requested
#3 task.resume_requested
#4 task.paused
#5 task.resumed
```

A separate client appends the resume request while the PM is publishing its pause acknowledgement. The PM immediately applies its returned `task.paused` event locally, before consuming the earlier concurrent resume request from the stream.

Observed:

```text
Running PM task status: open
Fresh ordered replay:  paused
```

On ordered replay, resume request #3 arrives before the task is paused and is rejected. The running PM has already optimistically applied #4, so it accepts #3 and emits #5.

### Impact

Restarting the PM or using a read-only observer can change the apparent outcome. This violates the central event-sourcing invariant that the persisted log determines one state.

### Recommended fix

- Maintain one ordered projection cursor.
- Consume coordination events strictly in event-ID order.
- After publishing an effect, catch up through its returned ID, including intervening events, rather than applying only the returned response.
- Avoid double-applying effects when SSE later delivers them.
- Handle an effect invalidated by concurrent commands as a stale plan requiring reconciliation, rather than automatically a fatal error.
- Specify whether resume arriving before pause acknowledgement is rejected or queued. Either policy must produce identical live and replay behavior.

### Regression acceptance criterion

Inject concurrent commands between planning and append, then assert that the live projection equals a fresh ordered replay of the persisted history.

Scratch reproduction: `/tmp/ab-v010-ordering.py`. Its final assertion intentionally fails on the reviewed code with `LIVE/REPLAY DIVERGENCE`.

## 2. High — Workflow pause is not consistently enforced by the reducer

**Locations:** `projection.py:782–834` (`task.assigned`), `projection.py:906–925` (`task.assignment_expired`).

The planner skips ordinary effects for paused workflows, but corresponding reducer branches do not consistently apply the workflow gate.

### Confirmed expiry scenario

```text
Task assigned with max_retries=0
→ workflow.pause_requested
→ previously planned task.assignment_expired arrives
→ retryable_failures becomes 1
→ workflow.paused
→ workflow.resume_requested / workflow.resumed
→ PM emits task.failed
```

The pause is intended to interrupt execution without charging a retryable failure. Instead, a late expiry consumes the budget and causes terminal failure after resume.

### Confirmed reducer-level assignment scenario

```text
Task created
→ workflow.pause_requested
→ workflow.paused (no active assignments)
→ late task.assigned
→ workflow resumed
→ completion of that assignment accepted
```

Fresh replay accepts this sequence. This establishes a missing reducer guard, not merely retention of a rejected event in the audit log. The exact assignment-after-ack sequence was constructed at reducer level; its reachability through a correctly operating single-PM deployment was not established.

### Recommended fix

- Apply workflow pause guards when reducing ordinary assignment/expiry effects, not only when planning them.
- Audit sibling ordinary PM transitions for the same inconsistency.
- Preserve cancellation and deadline authority during pauses.
- Coordinate this change with finding 1: rejecting stale acknowledgements requires the PM to consume ordered history and reconcile safely.
- Consider runtime handling of assignments arriving after a pause command, rather than assuming revoking currently owned assignments covers all arrival orderings.

### Regression acceptance criteria

- Expiry arriving after workflow pause request must not consume retry budget.
- Assignments arriving under an active workflow pause must not become executable valid attempts merely because the workflow later resumes.
- Test late PM effects as well as late worker outcomes.

Scratch reproductions:

- `/tmp/ab_v010_projection_repros.py`
- `/tmp/ab_v010_projection_cross_controls.py`

## 3. Medium — Concurrent identical supersession requests can fail idempotent replay

**Locations:** `bus.py:1258–1273`, `bus.py:1328–1344`, `bus.py:1389–1410`.

### Reproduction

Two identical replacement requests use the same actor and idempotency key. Both complete the initial lookup before either writes. One commits its supersession claim and event; the other hits the claim uniqueness constraint before reaching the event-insert idempotency recovery path.

Observed:

```text
Request A: replacement event #2
Request B: EventValidationError — task 1 already has a replacement at event #2
Sequential identical retry: event #2
```

The database retains exactly one replacement. Uniqueness holds, but concurrent retry behavior is incorrect. Through the HTTP exception mapping, this validation failure becomes a 422 response.

### Recommended fix

On a supersession-claim conflict, check for an already-committed event with the same actor/key and run the logical idempotency comparison before rejecting a genuinely different replacement. Alternatively, serialize the initial lookup with the write transaction.

Check the sibling external-origin claim path for the same pattern; this review's reported reproduction specifically exercised supersession.

### Regression acceptance criterion

Concurrent identical requests both return the same event. Conflicting payloads or genuinely different replacement requests still fail, and failed writes leave no orphan claims.

Scratch reproduction: `/tmp/ab-v010-bus-repro.py`.

## 4. Medium — Replaced failed intent can be revived and scheduled again

**Locations:** `projection.py:554–568`, `projection.py:999–1021`, `pm_agent.py:379–399`.

### Reproduction

```text
Old task fails permanently
→ replacement task.created supersedes the failed task
→ task.retry_requested targets the old task.failed event
→ old task becomes open
→ PM selects the old task for assignment
```

Observed:

```json
{
  "old_status": "open",
  "replacement_link": 2,
  "next_assignment_task": 1
}
```

### Impact and policy question

The old task retains `superseded_by_task_id`, but that relationship does not prevent revival. Preserving the old terminal outcome for history is sensible; allowing replaced intent to execute again is a separate semantic decision.

### Recommendation

Reject revival of replaced tasks by default, or require an explicit operation authorizing execution alongside the replacement. Document and test the chosen policy rather than letting the interaction be accidental.

Scratch reproduction: `/tmp/ab-v010-semantics.py`.

## 5. Low — Pause explanations hide deadline termination pending

**Locations:** `operations.py:139–170`, `operations.py:225–231`.

### Reproduction

For a paused task whose persisted deadline has passed:

```text
explain_task: Task is paused
PM next effect: task.deadline_exceeded
```

The explanation returns on task/workflow pause state before checking the expired deadline.

### Impact

An operator may think the system is waiting for resume when it actually needs deadline reconciliation. This is particularly confusing when the PM is down or lagging.

### Recommendation

Show deadline termination pending before ordinary paused/waiting explanations, while retaining pause details as context. Preserve the precedence of already-terminal outcomes and previously accepted terminal commands.

Scratch reproduction: `/tmp/ab-v010-semantics.py`.

## Conditional observation — Redelivery of an old control event

**Location:** `projection.py:329–344`.

After a full workflow pause/resume cycle, directly redelivering the original pause event re-pauses the workflow and moves `last_event_id` backwards. Reproduced at reducer level, but not established as a production delivery-path defect: normal fresh replay processes unique event IDs in order.

Do not present this as a separate confirmed operational bug without tracing the delivery contract. An ordered projection cursor and duplicate-event policy from finding 1 should explicitly address it.

## Checks that passed

- All four combinations of task-first/workflow-first pause and task-first/workflow-first resume preserved the other pause and eventually selected attempt 2.
- Cancellation and deadline termination rejected stale task-resume acknowledgements.
- Supersession uniqueness held across different actors.
- Failed replacement validation rolled back earlier claim writes.
- Replacement chains inherited workflow identity.
- Supersession claim rebuilding from scratch history restored uniqueness checks.
- Task pause/resume inherited target correlations and rejected nonexistent targets or correlation conflicts.
- Workflow controls rejected nonexistent workflows.
- Concurrent identical pause/resume commands returned the same event in focused checks.

## Recommended next steps

1. Fix ordered PM projection consumption and add live-versus-replay equality tests.
2. Make ordinary reducer transitions respect workflow control gates.
3. Repair concurrent supersession idempotency.
4. Decide revival semantics for replaced intent.
5. Align explanations with deadline/control precedence.
6. Add a state-machine/interleaving test suite covering combinations of pause, resume, completion, expiry, cancellation, and supersession.
7. Run isolated live executor trials after those fixes.
8. Only then add per-workflow concurrency limits and fairness. Define budget semantics separately before implementing token/cost limits.
